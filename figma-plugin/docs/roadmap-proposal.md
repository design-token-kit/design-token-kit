## 1. Принцип разделения

**Что проверяем.**

- **Токены.** Проверяется сама система токенов: переменные, стили, слои,
  ссылки и режимы. Результат не зависит от того, что нарисовано на холсте.
  Поэтому одни и те же проверки работают и на `tokens.json` в CLI, и на
  Figma Variables в плагине.
- **Дизайн.** Проверяются макеты, то есть узлы на холсте: читается ли текст,
  привязаны ли свойства к токенам. Результат зависит от области (страница или
  весь файл). Эти проверки есть только в Figma.

**Где живёт код.**

| Пакет | Роль |
| --- | --- |
| **core** | Модель токенов и все правила, которые работают с данными, а не с Figma: проверки `DtcgList`, расчёт контраста, score, сравнение наборов токенов. Работает в Node и в браузере. |
| **cli** | Обёртка над core для файлов, CI и агентов: ввод и вывод, коды выхода, форматы отчётов. Собственной логики проверок нет. |
| **figma-plugin** | Адаптер Plugin API: переводит Variables, Styles и узлы в модели core и показывает результат в UI. Сам решает только то, что без Figma не решить: обход узлов, фон под текстом, привязки `boundVariables`, выделение узлов. |

Правило: если проверку можно сформулировать без Plugin API, она пишется в core,
а плагин только собирает для неё данные. Так плагин и CLI на одних данных дают
одинаковый результат. Ради этого и делалась #97.

## 2. Что уже есть

### core и CLI (`dtokens`)

| Команда | Возможности |
| --- | --- |
| `check` | Схема DTCG 2025.10. Ссылки: неразрешённые, циклические, на группу. Несовпадение типов, дубликаты стопов градиента, устаревшие токены. Lint: `root-layer`, `layer-reference`, `raw-value-usage`, `empty-group`, `missing-description`, а также Tailwind-неймспейсы и rem base. |
| `audit` | Контраст текста и фона по WCAG, размер шрифта, line-height. Пары цветов определяются по ролям токенов. Score 0–100 и оценка A–F. |
| `convert` | Конвертация DTCG JSON ↔ HRDT YAML ↔ DESIGN.md. Генерация CSS, SCSS, Tailwind v4, SwiftUI, Android XML и скрипта для Figma. Темы. |
| `showcase` | HTML-витрина токенов. |
| `stats` | Статистика по токенам: текст или HTML. |

Кроме того, есть browser API и веб-интерфейс.

### Figma-плагин

| Вкладка | Возможности |
| --- | --- |
| **Export** | Variables и Styles выгружаются в DTCG, а затем в CSS, SCSS, Tailwind, Android и SwiftUI. Режимы становятся темами, алиасы сохраняются. |
| **Tokens** (анализ архитектуры) | Проверки core (`validationChecks` и `lintingChecks`) на переменных, статистика по слоям, score. |
| **Design** | Аудит текста на холсте: контраст по WCAG AA, текст мельче 12px, плотный line-height, группа «Not checked». Score, оценка A–F, переход к узлу. Подробно описано в `design-audit.md`. |

## 3. Вкладки плагина

Четыре категории из #91 ложатся на две вкладки, по две на каждую.

| Вкладка | Категории | Вопрос, на который отвечает | Источник данных |
| --- | --- | --- | --- |
| **Tokens** | Structure, Consistency | Правильно ли устроена система токенов? | Variables и Styles → `DtcgList` → core |
| **Design** | Accessibility, Token usage | Можно ли прочитать макет и собран ли он из токенов? | Узлы холста → модели core и проверки плагина |

У каждой вкладки свой score, потому что это разные вопросы к разным
объектам. Общий отчёт (см. [экспорт отчёта](#этап-1-закрыть-mvp-аудита-91-97))
может объединять обе вкладки, но баллы в нём не складываются.

Позже могут появиться ещё две вкладки (пока не делаем):

- **Sync**: импорт DTCG в Figma (#74), сравнение Figma с репозиторием и
  синхронизация (#22).
- **Report** не нужна отдельной вкладкой, достаточно кнопки «Скопировать или
  скачать отчёт» на Tokens и Design.

## 4. Проверки: где живут и где показываются

Обозначения в столбце «Статус»: ✅ есть, 🟡 частично, ⬜ нет.

### Tokens: Structure

| Проверка | Правило | CLI | Плагин | Статус | Задача |
| --- | --- | --- | --- | --- | --- |
| Токены вне слоёв primitive/semantic/component | core `root-layer` | ✅ | Tokens | ✅ | #87 |
| Запрещённые ссылки между слоями | core `layer-reference` | ✅ | Tokens | ✅ | #9, #10 |
| Сырые значения не в primitive | core `raw-value-usage` | ✅ | Tokens | ✅ | |
| Изоляция компонентов | плагин `component-isolation` → перенести в core | ⬜ | Tokens | 🟡 | #97 |
| Битые и циклические ссылки, ссылки на группу | core `bad-reference` | ✅ | Tokens | ✅ | |
| Несовпадение типов | core `type-mismatch` | ✅ | Tokens | ✅ | |
| Пустые группы, нет описания | core | ✅ | Tokens | ✅ | #13, #14 |
| Глубина цепочки алиасов больше N | core, новое | ⬜ | Tokens | ⬜ | #8 |
| Алиасы, которые нельзя представить в Figma | плагин: предупреждения экспорта | — | Tokens | 🟡 | #91 |

### Tokens: Consistency

| Проверка | Правило | CLI | Плагин | Статус | Задача |
| --- | --- | --- | --- | --- | --- |

| Расхождения режимов: в режиме нет значения, в одном режиме алиас, а в другом сырое значение, разные типы | core `required-modes`, новое | ⬜ | Tokens | ⬜ | |
| Ссылки на устаревшие (`$deprecated`) токены | core | ✅ | Tokens | 🟡 (проверить, что выводится в плагине) | |

### Design: Token usage

Почти все проверки этой категории читают узлы, поэтому живут в плагине.

| Проверка | Где | Статус | Задача |
| --- | --- | --- | --- |
| Захардкоженные цвета, отступы, радиусы, размеры шрифта (`hardcoded-value`) | core: правило, плагин: сбор свойств | ✅ | #91 |
| Подсказка «Match»: ближайшая переменная или стиль для захардкоженного значения | core `TokenMatcher`, плагин: кандидаты из локальных Variables и Styles | ✅ | #91 |
| Узел на холсте привязан к primitive при наличии semantic (`primitive-binding`) | core: правило, плагин: сбор привязок | ✅ | #91 |

| Detached styles: значение совпадает со стилем, но стиль не применён | частично: подсказка стиля в `hardcoded-value`; отдельной проверки нет | 🟡 | #91 |

## 5. Что интересного у других

Короткий обзор. Подробные данные о конкурентах хранятся в
`internal/comparison/comparison.yaml` (#49), этот раздел его дополняет.

| Инструмент | Что взять |
| --- | --- |
| **DTCG Resolver Module 2025.10** | Описание тем и режимов в `.resolver.json` (`sets`, `modifiers`, `contexts`). Режимы Figma естественно ложатся на `modifiers`. Это стандартная замена нашей схеме «первый файл базовый, остальные темы». |
| **Terrazzo** (ближайший open-source аналог) | Набор lint-правил: `consistent-naming`, `duplicate-values`, `required-modes`, `max-gamut`, `colorspace`, `descriptions`, `a11y/min-contrast` (пары fg/bg объявлены в конфиге), `a11y/min-font-size`. Плагинный API в стиле ESLint. `token-listing`: карта «токен → имя на каждой платформе». Импорт из Figma в `.resolver.json`. |
| **Style Dictionary v5** | Стандарт де-факто для сборки. Нужна совместимость: экспорт или импорт в формате SD. |
| **Tokens Studio** | Двусторонняя синхронизация с Git, генерация шкал (Graph Engine), экспорт `scopes` и `codeSyntax`. |
| **Supernova** | Отдаёт контекст дизайн-системы агентам через MCP. |
| **zeroheight** | Изменения токенов приходят в репозиторий как pull request, а не прямым коммитом. |
| **Figma Check designs** | Находит захардкоженные значения, подсказывает переменную с пометкой «Match», проверяет контраст. Ограничения: только платные планы Organization и Enterprise, одна страница. Нельзя отметить намеренное исключение, это самая частая жалоба пользователей. |
| **Figma, нативный экспорт DTCG** | По отзывам на форуме теряет описания и составные токены (shadow, typography). Наш экспортёр закрывает эти пробелы, это стоит подчеркнуть. |
| **Figma REST API** | Variables и Library Analytics доступны только на Enterprise. Наш плагин работает через Plugin API на любом плане, это сильное преимущество. |
| **Atomize** | Coverage Audit (доля привязанных свойств) и Find Untokenized Values (13 типов свойств, подсказка токена, экспорт, пропуск намеренных значений). |
| **FigmaLint, Design Lint** | Привязка захардкоженного значения к переменной одним кликом. |
| **Stark** | APCA в бете, симуляция нарушений зрения, порядок фокуса. |
| **stylelint `use-design-tokens`** (Mozilla) | Ищет захардкоженные значения в CSS и автоматически заменяет их на токены. |
| **token-reconciler, Fixel** | Проверка расхождений между Figma и кодом в CI с кодами выхода и комментариями к PR или к узлам Figma. |
| **Omlet** | Аналитика использования компонентов в коде. |

Чего мы не нашли ни у кого целиком: семантического diff токенов с подсказкой
semver и комментарием в PR. Каждая команда собирает такое сама. Это свободная
ниша.

## 6. Дорожная карта

### Этап 1. Закрыть MVP аудита (#91, #97)

- **Tokens.** Перенести оставшиеся проверки плагина в core, удалить
  собственный анализатор (#97).
- **Design → Token usage.**
  - Захардкоженные значения с подсказкой «Match».
  - Привязка узлов к primitive.
  - Покрытие токенами в процентах.
  - Detached styles.
- **Design → Accessibility.** Переключатель AA/AAA.
- **Обе вкладки.**
  - Фильтр по категории.
  - Экспорт отчёта в Markdown и JSON (копирование и скачивание).
  - Описание в документации, что проверяет каждая вкладка.
- **Демо.** Демонстрационный Figma-файл с положительными и отрицательными
  кейсами (DoD #91, playground #73).

### Этап 2. Согласованность токенов в core

- Новые правила:
  - `duplicate-values` и поиск почти одинаковых значений;
  - соглашение об именовании;
  - `required-modes` (расхождения режимов);
  - глубина алиасов;
  - охват цветов (gamut);
  - неиспользуемые токены (#11);
  - расхождение `hex` и `components` (#93).
- Единая модель finding для `check` и `audit`, единый score.
- Конфиг severity правил и исключения.
- Контрастные пары, объявленные в токенах, для `dtokens audit`.

### Этап 3. Синхронизация и CI

- `dtokens diff`: добавленные, удалённые, переименованные токены, изменённые
  значения. Подсказка semver и changelog в Markdown.
- GitHub Action и pre-commit hook (#23): `check`, `audit`, `diff` и комментарий
  к PR.
- Проверка расхождений между Figma и репозиторием. Плагин выгружает текущее
  состояние, CLI сравнивает его с репозиторием и падает при конфликте (#22).
- Импорт DTCG в Figma (#74), затем двусторонняя синхронизация (#22).
- Поддержка `.resolver.json` для тем и режимов.
- Мост к Plugin API (#75) для автоматических проверок Figma-файлов без UI.

### Этап 4. Код, агенты и рефакторинг

- `dtokens scan`: поиск захардкоженных значений в CSS и SCSS с подсказкой
  токена, или плагин для stylelint.
- Инспектор токенов в браузере (#95) и карта «токен → CSS-переменная». Та же
  карта нужна для `token-listing` и для записи `codeSyntax` в переменные Figma
  (Dev Mode).
- MCP-сервер или скилл для агентов (#47): найти токен, проверить, показать
  отчёт аудита.
- Рефакторинг: переименование токена с обновлением ссылок (#19), перенос
  между слоями (#21).
- Метрики: сложность дизайн-системы (#7), health score всей системы (#8).
- Генерация шкал цветов и отступов.
- Конвертация в другие форматы и обратно (#24), CSS → токены (#17).

## 7. Открытые вопросы

1. **Область аудита Design по умолчанию.** Страница, выделение или весь файл?
   Сейчас страница. Неиспользуемые переменные имеют смысл только при «Entire
   file».
2. **Источник токенов для проверки Token usage.** Только локальные Variables и
   Styles, или ещё подключённые библиотеки, или загруженный DTCG?
3. **Score.** Оставить отдельный на каждой вкладке или добавить общий? Нужны
   ли веса, которые настраивает пользователь?
4. **Где хранить исключения.** В `pluginData` узла (видно только нашему
   плагину) или в токенах и конфиге (видно и CLI)?
5. **APCA.** Показывать как справочную метрику? В WCAG 3 метод контраста ещё не
   выбран.
6. **Resolver Module.** Переходить ли на `.resolver.json` вместо схемы «база +
   темы», и когда?
7. **Автоисправление.** Привязку к переменной одним кликом в #91 не включали.
   Когда она появится, аудит перестанет быть только для чтения.
